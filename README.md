# My Market App

Веб-приложение интернет-магазина. Каталог, корзина и заказы хранятся в PostgreSQL 
через R2DBC; данные товаров кешируются в Redis. Отдельный реактивный сервис платежей предоставляет баланс и 
списывает стоимость заказа.

## Структура

| Модуль / каталог | Назначение |
|---|---|
| `my-market-app-bom` | Управление версиями зависимостей |
| `my-market-app-api` | Контракты контроллеров магазина и DTO добавления товара |
| `my-market-app-impl` | Магазин, PostgreSQL, Redis, клиент платежей |
| `payment-service` | Отдельное приложение платежей на WebFlux |
| `openapi/payments.yaml` | Общий контракт интеграции магазина и платежей |

## Возможности

- Каталог с поиском по названию и описанию без учёта регистра.
- Сортировка товаров по названию или цене и постраничный просмотр.
- Страница товара с описанием, изображением, ценой и количеством в корзине.
- Добавление товаров, изменение количества и удаление позиций из корзины.
- Расчёт стоимости корзины и оформление заказа с последующей очисткой корзины.
- История заказов и просмотр состава отдельного заказа с изображениями товаров.
- Загрузка изображений из файловой системы с заглушкой для отсутствующих файлов.
- Автоматические миграции БД и опциональная загрузка демонстрационных данных.
- Проверка баланса при открытии корзины; покупка отключается при недостатке средств или недоступности платежей.
- При покупке сервер заново рассчитывает сумму по данным БД и отправляет платёж. После успешной оплаты оформляется заказ и очищаются купленные позиции корзины.
- При ошибке оплаты изменения заказа и корзины откатываются; пользователь возвращается в корзину с сообщением.
- История заказов со снимками названий, цен, изображений и количества товаров на момент покупки.
- Добавление товара с изображением через веб-форму.

В приложении нет пользователей и авторизации: корзина и история заказов общие для всех посетителей. Оформление заказа сохраняет покупку в БД.

## Сборка и тесты

Требуются JDK 21, Maven Wrapper из репозитория и доступ к Maven Central при первой сборке. Для полного набора 
тестов нужен запущенный Docker: Testcontainers поднимает PostgreSQL и Redis. Тесты используют JUnit 5, 
Spring Boot Test, Mockito, WebTestClient и StepVerifier; общие конфигурации позволяют повторно использовать 
тестовые контексты.

Все команды выполняются из корня проекта. В Windows используйте `mvnw.cmd` вместо `./mvnw`.

```sh
# Сборка обоих приложений и запуск всех тестов.
./mvnw clean verify

# Только сервис платежей и его тесты, без Docker.
./mvnw -pl payment-service -am test

# Получение JAR без запуска тестов.
./mvnw package -DskipTests
```

## Запуск через Docker Compose

```sh
docker compose up --build -d
```

Поднимаются четыре сервиса: `app`, `payments`, `db`, `redis`.

- Магазин: [http://localhost:8080](http://localhost:8080).
- Баланс платежного счёта: [http://localhost:8081/api/balance](http://localhost:8081/api/balance).
- Redis: `localhost:6379`.

В Compose включены демо-данные, изображения подключены из `./images`. Загруженные через форму изображения 
сохраняются в томе `image-uploads`, PostgreSQL — в томе `postgres-data`. Redis используется только как кеш; его 
данные можно восстановить из БД.

Начальный баланс по умолчанию — `100000.00` рублей.

Остановка:

```sh
docker compose down
```

## Конфигурация

| Переменная | Значение по умолчанию / пример | Назначение |
|---|---|---|
| `R2DBC_URL` | `r2dbc:postgresql://localhost:5432/my_market_app` | Обязательное реактивное подключение к БД |
| `JDBC_URL` | `jdbc:postgresql://localhost:5432/my_market_app` | Обязательное подключение Liquibase |
| `DB_USERNAME`, `DB_PASSWORD` | `market` | Обязательные учётные данные БД |
| `DB_SCHEMA` | `public` | Существующая схема БД |
| `SERVER_PORT` | `8080` | Порт магазина |
| `REDIS_HOST`, `REDIS_PORT` | `localhost`, `6379` | Подключение к Redis |
| `PRODUCT_CACHE_TTL` | `PT2M` | TTL данных товаров |
| `PRODUCT_CACHE_TIMEOUT` | `PT0.5S` | Максимальное ожидание операции кеша |
| `PAYMENT_BASE_URL` | `http://localhost:8081` | Адрес сервиса платежей для магазина |
| `PAYMENT_TIMEOUT` | `PT3S` | Таймаут подключения и платёжного запроса |
| `PAYMENT_SERVER_PORT` | `8081` | Порт сервиса платежей |
| `PAYMENT_INITIAL_BALANCE` | `100000.00` | Начальный баланс сервиса платежей |
| `IMAGES_ROOT` | `images` | Каталог изображений магазина |
| `IMAGES_DEFAULT_IMAGE` | `default-image.svg` | Заглушка внутри каталога изображений |
| `INSERT_DEMO_DATA` | `false` | Однократная загрузка демонстрационных данных |

Длительности задаются в формате ISO-8601 Duration. Например, `PT2M` — две минуты, `PT3S` — три секунды.

## Кеширование товаров

Логика кэширования находится в сервисах: сначала чтение через `ProductCacheRepository`, при отсутствии — 
PostgreSQL с последующим заполнением кеша. Отдельно кешируются карточки товаров и страницы каталога с общим 
количеством найденных товаров. Ключ страницы зависит от поиска, сортировки, номера и размера страницы. Данные 
включают идентификатор, название, описание, цену и путь к изображению.

Корзина берёт из БД идентификаторы и количества, затем загружает данные товаров пакетно через тот же кеш карточек. 
Отсутствующие в Redis товары читаются одним запросом к БД. Количество и общая корзина в Redis не сохраняются. 
При недоступности или таймауте Redis магазин читает БД; TTL ограничивает время хранения устаревших товаров. 
`ItemServiceImpl` инвалидирует страницы каталога после успешного добавления товара. Ручные изменения в БД 
становятся видны после TTL.

## API сервиса платежей

Контракт: [openapi/payments.yaml](openapi/payments.yaml). Обмен — JSON, суммы — в рублях с точностью до копеек.

```sh
curl http://localhost:8081/api/balance

curl -X POST http://localhost:8081/api/payments \
  -H 'Content-Type: application/json' \
  -d '{"amount":125.50}'
```

Успешный ответ: `{"balance":99874.50}` при исходном балансе `100000.00`.

- Невалидный запрос: HTTP 400, код `INVALID_REQUEST`.
- Недостаточно средств: HTTP 409, код `INSUFFICIENT_FUNDS`.

Каждый успешный запрос списывает указанную сумму, включая повторные запросы с той же суммой.

Баланс хранится в памяти. После перезапуска он сбрасывается к начальному значению. Идемпотентность оплаты не 
реализована в целях упрощения сервиса.

Оплата выполняется после успешных SQL-операций, перед коммитом транзакции магазина. При отказе платежей 
транзакция откатывается. Общей транзакции между PostgreSQL и HTTP нет: при потере ответа после списания или 
ошибке коммита возможна неопределённость результата. Магазин не повторяет платёж автоматически. 
Для промышленной эксплуатации нужны сохраняемые платёжные попытки, восстановление статуса и согласование состояний.

## Добавление товара

В каталоге нажмите **«Добавить товар»**. Укажите название, описание и цену, выберите изображение и нажмите 
**«Добавить товар»**. После сохранения откроется карточка нового товара. Ошибки отображаются в форме; введённые 
текстовые поля сохраняются, файл при повторной отправке нужно выбрать заново.

Форма отправляется на `POST /items/new` как `multipart/form-data` с полями `title`, `description`, `price`, `image`. 
Поддерживаются PNG и JPEG размером до 5 МиБ; сервер проверяет формат файла. Существующие товары не обновляются.

Пути и имена файлов формирует сервер: изображения сохраняются в `IMAGES_ROOT/uploads`, а в БД записывается 
относительный `imagePath`. `ItemService` сохраняет изображение и одну запись товара; при ошибке записи файл удаляется. 
После успешной записи сбрасывается кеш страниц каталога.

При локальном запуске `IMAGES_ROOT` должен быть доступен приложению для записи. В Docker каталог `uploads` 
подключён отдельным томом, доступным пользователю приложения. Выдача изображений проверяет, что файл, в том 
числе после разрешения символических ссылок, находится внутри корневого каталога.

## Миграции

Liquibase автоматически применяет changelog из `my-market-app-impl/src/main/resources/db/changelog`. Демо-миграция 
добавляет 12 товаров и примеры заказов только при `INSERT_DEMO_DATA=true`. Без демо-данных каталог изначально пуст;
добавьте товары через веб-форму.
